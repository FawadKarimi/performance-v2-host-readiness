Read-only supplemental local captures from `performance-v2-metadata-reconciliation-20261004/reconciliation` were independently rehashed. The latter is selected by the former and names config digest `3abf66fa95bf9285d35eac802319797d29d01fbcfef9c0cd560f73d97f4289e8`. These existing text captures establish manifest/descriptor identities, not approved base-image selection, config/layer verification or an installed rootfs. No registry request or image pull occurred here. Exact capture files/descriptors are saved in root-source-and-target-evidence.json.

Before choosing native artifacts, reconcile an existing evidence packet for this exact image (or separately review a different immutable image):

1. Bind chosen manifest, config and layer/rootfs identities to the inspected image. Retain the actual config and inventory receipts and their hashes; a tag or descriptor alone is insufficient. The historical older image digest and 105-row inventory must not be reused as this new image's inventory.
2. Exact image `/etc/os-release`, libc implementation, libc6 package version/architecture and dynamic-loader/libc identity; actual glibc major/minor and applicable distro patch status. The GitHub runner's host glibc or the Windows reviewer runtime is not this evidence. Both preserved torch/vision artifacts require `manylinux_2_28_x86_64`, hence glibc >=2.28 even if another dependency offers a 2.17 wheel.
3. Exact CPython 3.12.15 executable/build identity, architecture, SOABI/EXT_SUFFIX and ABI flags; bind the effective installer and tag-engine version. Capture the **ordered supported-tag list** generated for that same target, with digest and generation provenance. The marker dictionary has intentionally blank platform-release/version and is not a native inventory.
4. Execution-host CPU features, including x86-64-v2 if NumPy 2.4/2.5 is considered. Container manifests do not prove those host capabilities. This can become a compatibility blocker despite a matching manylinux tag.
5. Relevant system and bundled-library inventory and provenance: dynamic loader/libstdc++/libgcc/OpenMP, image codecs, BLAS and OpenCV/FFmpeg/GUI dependencies as applicable. Package sidecars do not enumerate or verify all bundled native libraries. Exact-wheel SBOM/build evidence, later byte verification and compatibility remain distinct future gates.

Multiple compressed wheel tags are alternatives, not cumulative minimums. The reference NumPy 2.2.6 offers 2.17; NumPy 2.5.3 and Pillow 12.3.0 advertise 2.27/2.28; pandas 2.3.3 offers 2.24/2.28; PyYAML 6.0.3 offers 2.17/2.28. OpenCV has distinct 2.17 and 2.28 artifacts. Do not select either by age, size or identical metadata digest: ordered target tags and exact artifact evidence must govern. No source build fallback is authorized. See [PEP 600](https://peps.python.org/pep-0600/) (created 2019-05-03) and the dated NumPy evidence in native-support-security.md.

## Recursive gaps and the next proposal

The seven-request proposal covers one exact pure-wheel sidecar for each unresolved pure direct torch dependency. It is the smallest batch covering that entire frontier, not a claim that seven requests finish the graph. Existing torch/vision sidecars are not requested again. Native first-level children NumPy/Pillow and repository PyYAML/pandas/OpenCV remain deferred; wheel/pytest are separate build/test work, and pip lacks exact sidecar evidence.

After a separately authorized fetch, hash the raw sidecar bytes, validate Name/Version/Requires-Python and parse every Requires-Dist with the frozen target, extras and root intersections. Record inactive edges explicitly. SymPy→mpmath, Jinja→MarkupSafe, pandas→dateutil/pytz/tzdata, pytest→iniconfig/packaging/pluggy/Pygments and wheel→packaging are likely next-frontier examples, not exact verified pins. Authoritative constraints come from the exact sidecars. New child artifact URLs/hashes cannot be manufactured from names or release-level JSON; the existing fourteen indexes may resolve some children, others need a distinct bounded proposal. All eventual child uploads must satisfy the SAME frozen cutoff, including patch releases. No dynamic fetch or open recursion is allowed by this proposal. [PEP 658](https://peps.python.org/pep-0658/) defines the artifact-bound metadata mechanism (created 2021-04-21).

Full Docker acceptance remains pending. Stage A's accepted bounded closure is preserved; Stage B and GPU pilots remain paused.
